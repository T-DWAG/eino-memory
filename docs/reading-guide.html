阶段 1 · 契约：两个接口

整个项目的骨架

目标：理解「记忆策略」和「调 LLM」都被抽象成了接口，后面所有代码都围绕它们展开。

  • Strategy 接口（L14）：4 个方法，都带 context.Context 和错误返回值
  • Message / Turn：策略内部存储用的数据结构
  • formatMessages / formatTurn：各策略共用的格式化函数，后面会反复见到
自测：为什么 GetContext 要接收 query，而顺序记忆明明用不到？

接口要覆盖所有策略。检索、图、OS 换页都要用 query 做相关性查找，用不到的策略写成 _ string 忽略就行。

TextGenerator 接口只有一个方法。重点是它定义在 memory 包里，而不是 llm 包里。
自测：如果把 TextGenerator 挖到 llm 包里定义，会发生什么？

memory 就得 import llm，依赖反了方向；写 memory 的测试也会连带引入 eino-ext openai。接口放在使用方，是 Go 的常见做法。

阶段 2 · 最简实现

纯内存，不调模型

目标：看懂一个策略的完整样子（锁 + 四个方法），后面的策略都是这个模板。

  • SequentialMemory：最简单的策略，留意 sync.RWMutex 的用法
  • SlidingWindowMemory：用切片截断保留最近 N 轮（L80）
自测：截断时为什么用 append([]Turn(nil), ...) 复制一份，而不是直接 m.turns = m.turns[1:]？

直接切片会一直引用同一个底层数组，前面被丢弃的元素无法被 GC 回收。复制一份后旧数组就能释放。

看滑动窗口的效果：第 3 轮后名字被淘汰。
go test ./memory -run SlidingWindow -v

阶段 3 · Agent 与 eino 编排

整个项目中 eino 用得最多的地方

目标：看懂一次 Chat 是怎么用 compose.Chain 串起来的。读完可以回头看 architecture.html 的图 ③。

  • L67 InvokableLambda：把「读记忆」包成一个节点，输出模板变量 map[string]any
  • L82 prompt.FromMessages(schema.FString, ...)：系统提示词也当变量传入
  • L87 NewChain[string, *schema.Message] → Append 三个节点 → L93 Compile
自测：系统提示词为什么写成 "{system}" 变量，而不是直接写死在模板里？

FString 会把模板里的 {xxx} 当作占位符。如果用户自定义的提示词里有花括号，写死会渲染报错。变量的“值”里有花括号则没问题。

L114 Invoke 跑 Chain；L121 读取模型返回的真实 token 用量；L127 成功后才写回记忆。
自测：为什么 AddMessage 不放在 Chain 里做最后一个节点？

放在外面能保证只有模型成功才写记忆，写失败也不影响本轮回复。代价是这一步不在 eino callbacks 里。两种都行，是取舍。

echoModel 实现了 model.BaseChatModel，可以直接看到模板渲染后实际发给模型的消息。想在 eino 里 mock 模型，可以参考这个写法。
go test ./agent -v

阶段 5 · 调 LLM 的策略

都依赖 TextGenerator，按难度递增

目标：理解「LLM 作为工具」的几种用法：压缩、摘要、抽取事实、抽取结构化数据。每读完一个就跑对应的 demo。

最简单的用法：每轮调一次 LLM，把结果存进列表。

自测：consolidate 是在持有锁的情况下调 LLM，有什么影响？

摘要期间其他读写会被阻塞。Agent.Chat 本来就是串行的，所以 demo 里没影响；做成高并发服务时可以改成「拷出缓冲区 → 解锁 → 调 LLM → 再加锁写回」。

第一个组合型策略：内部持有一个 SlidingWindowMemory。noFactMarker（L25）用来和 LLM 约定「没有需要记住的事实」。
go run ./cmd/demo -s augmented
  • L67 extractTriples：先按 JSON 解析，失败了再用元组正则兜底
  • L117 GetContext：用子串匹配做实体链接，中文也能用

阶段 6 · 向量检索

自己实现 eino 的 Indexer / Retriever

目标：学会怎么实现 eino 的标准组件接口，理解从底层向量库到层次化记忆是怎么一层层叠上去的。

  • L35 的 var _ indexer.Indexer = ...：在编译期检查是否实现了接口
  • Store / Retrieve 里的 GetCommonOptions：eino 组件处理 Option 的标准写法
  • cosine：用余弦相似度衡量文本相关度
自测：Retrieve 里为什么要复制文档，还要单独复制 MetaData？

WithScore 会往 MetaData 这个 map 里写分数。不复制，就是在读锁外面改存储里的原始文档；只做浅拷贝，两份文档仍共享同一个 map。两种情况在并发检索时都会出现数据竞争，所以要连 map 一起复制。

只是在向量库外面包了一层。用户输入和 AI 回复各存成一个文档。
go run ./cmd/demo -s retrieval
把之前读过的两个策略组合起来：滑动窗口做工作记忆，检索记忆做长期记忆。对照 architecture.html 图 ② 右侧那一列。
go test ./memory -run "Retrieval|Hierarchical" -v
go run ./cmd/demo -s hierarchical

自测：为什么遍历 passive 前要先排序 ids？

Go 的 map 遍历顺序是随机的。不排序的话，每次换入的顺序都可能不同，发给模型的 Prompt 也就不稳定。

把关键词匹配换成 InMemoryVectorStore：换出时 Store，查询时 Retrieve。测试里可以直接用 fakeEmbedder。
用 callbacks.NewHandlerBuilder() 写一个 handler，在 Invoke 时用 compose.WithCallbacks 传进去，打印每个节点的耗时。
现在一个 Agent 只对应一个记忆。可以做一个 map[sessionID]memory.Strategy 加一个工厂函数，让 Chat 接收 sessionID。
