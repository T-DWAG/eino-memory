9 种记忆策略 · 代码讲解稿

对着 go-eino-memory/memory/ 讲。所有策略实现同一个接口，Agent 只依赖接口。

开场：共同契约

memory/memory.go · Strategy 接口

所有策略都实现这同一个接口，就四个方法：

  • Name() —— 返回策略名，日志用。
  • AddMessage(ctx, userInput, aiResponse) —— 写入一轮对话。
  • GetContext(ctx, query) —— 返回要拼进 Prompt 的上下文。
  • Clear() —— 清空。

注意 GetContext 带 query 参数——顺序、滑动这些策略用不到它，但检索、图、OS 都要靠它做相关性查找。另外两个辅助类型 Message（角色 + 内容）和 Turn（一轮对话），加上 formatMessages、formatTurn 两个格式化函数，后面每个策略都会用到。

记住一句话：这 9 种策略，本质都是在决定"这一轮上下文里放什么"，区别只是取舍方式不同。

图例： 策略类型（绿实线） memory 自定接口 TextGenerator（橙虚线） eino 标准接口（灰虚线） 数据字段（灰细线）  ·  嵌套 = 内部持有

1 顺序记忆 Sequential

memory/basic.go · SequentialMemory

SequentialMemory
memory/basic.go
history []Message — 全量历史

什么都不丢，全量塞给模型。它是后面所有策略的"基准线"。

  • AddMessage：把用户消息和助手消息依次 append 进 history，一条不落。
  • GetContext：把整个 history 用 formatMessages 拼成文本，全量返回。
代价：token 随轮次线性增长，迟早撞上下文窗口。其他策略都是在它基础上做减法。

适合：demo、短对话、调试。

2 滑动窗口 Sliding Window

memory/basic.go · SlidingWindowMemory

SlidingWindowMemory
memory/basic.go
turns []Turn — 只留最近 N 轮

只保留最近 N 轮，旧的自动丢弃。

  • AddMessage：追加一轮，如果 len(turns) > windowSize，就只保留最后 N 轮。
  • GetContext：把窗口内的轮次拼成消息列表返回。
实现细节：截断用 append([]Turn(nil), turns[...]...) 复制一份，而不是直接切子切片——否则旧元素占着底层数组，GC 收不掉。

效果：第 4 轮问第 1 轮的名字，窗口里已经没这信息了。
适合：通用聊天，只看近期上下文。

3 摘要记忆 Summarization

memory/summarization.go · SummarizationMemory

SummarizationMemory
memory/summarization.go
TextGenerator
调 LLM 合并摘要
runningSummary string
buffer []Message
threshold int

消息先进缓冲区，满了让 LLM 合并成滚动摘要。第一个要调 LLM 的策略。

  • AddMessage：消息进 buffer；达到 threshold 就触发 consolidate。
  • consolidate：把"旧摘要 + 缓冲区"拼成 prompt 交给 LLM，得到新摘要，覆盖 runningSummary，清空 buffer。
  • GetContext：返回 runningSummary + 还没被摘要的 buffer。
TextGenerator 接口就一个 GenerateText 方法，定义在 memory 包自己里面，llm.Client 隐式实现它——这样 memory 不用 import llm。另外 consolidate 失败时不清空 buffer，避免丢数据。

适合：长对话、创作类，用 token 换信息密度。

4 检索记忆 Retrieval（RAG）

memory/retrieval.go · RetrievalMemory，核心在 memory/vectorstore.go

RetrievalMemory
memory/retrieval.go
InMemoryVectorStore
memory/vectorstore.go
embedding.Embedder
eino 接口
Indexer + Retriever
本 store 实现这两个 eino 接口
docs · vectors

把历史向量化，查询时只取语义最相关的 topK 条。

  • AddMessage：把"用户说…"和"AI回复…"各存成一个文档，Store 时向量化写入。
  • GetContext：把 query 向量化，Retrieve 用余弦相似度算 topK，拼成上下文。
关键设计：InMemoryVectorStore 同时实现 eino 的 indexer.Indexer 和 retriever.Retriever，所以生产环境换成 Milvus / Redis / ES8，策略代码一行不用改。另一个细节：Retrieve 返回文档前，连 MetaData 这个 map 一起深拷贝，否则写分数时会并发写同一个 map。

适合：问答、知识型 Agent，需要精确召回具体事实。

5 记忆增强 Memory-Augmented

memory/augmented.go · MemoryAugmentedMemory

MemoryAugmentedMemory
memory/augmented.go
SlidingWindowMemory
短期窗口
TextGenerator
抽取长期事实
memoryTokens []string — 长期便签

短期窗口 + 长期"便签"。第一个组合型策略——内部持有另一个策略。

  • AddMessage：两步。先把本轮丢进 recent 短期窗口；再让 LLM 判断这轮有没有值得长期记住的事实，有就提炼成一句话存进 memoryTokens。
  • 判断方式：约定一个标记字符串 "无重要事实"，LLM 回复里含它就不存。
  • GetContext：把 memoryTokens 列表 + recent 近期对话拼在一起。
效果：过敏、ID 这类关键事实不会随窗口滑走。代价：每轮多一次 LLM 调用。

适合：需要可靠记住用户偏好的个人助理。

6 层次化记忆 Hierarchical

memory/augmented.go · HierarchicalMemory

HierarchicalMemory
memory/augmented.go
SlidingWindowMemory
工作记忆
RetrievalMemory
长期记忆
InMemoryVectorStore
memory/vectorstore.go
embedding.Embedder
promotionKeywords []string

两层：滑动窗口做工作记忆，向量检索做长期记忆。把策略 2 和策略 4 组合起来。

  • AddMessage：所有消息都进 working；只有含"记住 / 偏好 / 过敏"等关键词的消息才额外提升进 longTerm。
  • GetContext：长期检索结果 + 最近工作记忆，两层拼一起。
和策略 5 的对比：5 用 LLM 判断哪些值得长期记，6 用关键词启发式判断——更便宜，但会漏掉没带关键词的重要信息。

适合：既要流畅闲聊、又要记关键信息的复杂 Agent。

7 图记忆 Graph

memory/graph.go · GraphMemory

GraphMemory
memory/graph.go
TextGenerator
抽取三元组
nodes map — 实体
edges map — 关系（存边上）

把事实抽成 (主语, 关系, 宾语) 三元组，存成有向图，能回答需要跨事实推理的问题。

  • extractTriples：让 LLM 把文本抽成三元组，要求输出 JSON 数组；解析失败再用元组正则兜底。
  • AddMessage：抽三元组，subject、object 加进节点，subject → object 加进边，关系挂在边上。
  • GetContext：实体链接——找 query 里出现的节点，返回它的所有入边和出边。
实体链接用子串匹配而不是分词，所以中文（比如"告诉我关于Clara的项目"）也能命中节点 Clara。

适合：知识库、专家系统，需要关系推理的多跳问题。

8 压缩记忆 Compression

memory/compression_os.go · CompressionMemory

CompressionMemory
memory/compression_os.go
TextGenerator
压缩成一条事实
facts []string

每轮让 LLM 压缩成一条精简事实，只存事实列表。最省 token。

  • AddMessage：把本轮拼成文本，让 LLM 当"数据压缩器"提炼成一条事实，append 进 facts。
  • GetContext：把 facts 用 - 拼成列表返回。
和摘要的区别：摘要保留叙事、合并多轮；压缩是每轮独立压成一条硬事实，语气和细节全丢。

适合：会议纪要、任务清单这类只关心事实的场景。

9 类 OS 记忆 OS-Like

memory/compression_os.go · OSMemory

OSMemory
memory/compression_os.go
active []pagedTurn — RAM
passive map[int]string — Disk
turnCount int

模拟操作系统：RAM 只装最近几轮，满了换出到 Disk，命中时再"缺页"换入。

  • AddMessage：RAM 满时把最旧一轮换出到 passive，再把新轮追加进 active。
  • GetContext：返回 active，然后做缺页判断：query 的关键词命中 passive 里某轮，就把它换入拼上。
  • queryTerms：提取关键词——英文按空白切分取长度 > 3 的词，中文用相邻双字（bigram）。
两个细节：Go 的 map 遍历顺序随机，遍历 passive 前先对轮次号排序，否则输出不稳定；中文没有空格分词，加 bigram 匹配，否则"发射代码"这种纯中文问题永远触发不了缺页。

适合：跨天、跨周的长期运行 Agent。

收束

9 种策略，从"全放"到"只放最相关"，本质是 token 成本和信息保真之间的权衡。没有最优解，只看你的 Agent 需要记什么、记多久、要多精确。
